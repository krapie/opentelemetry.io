**상태**: [알파(Alpha)](/docs/specs/otel/document-status/)

**프로파일(profile)** 은 애플리케이션이 실행 중 어디에서 리소스를 소비하는지
보여주는 샘플(sample)과 관련된 메타데이터의 **모음**이다. 샘플은 특정 프로그램
컨텍스트(일반적으로 스택 트레이스(stack trace))에서 관찰된 값을 기록하며, 더
상위 수준의 요청에 해당하는 트레이스 ID와 같은 보조 정보로 보강될 수도 있다.

샘플을 캡처하는 순간을 **샘플 이벤트(sample event)** 라고 하며, 이는 관측 데이터
포인트뿐만 아니라 캡처된 시간도 함께 포함한다.

예를 들어 On-CPU 프로파일은 샘플이 캡처될 당시 CPU에서 실행 중이던 코드에 대한
샘플(집계된 스택 트레이스)과 함께, 각 스택 트레이스가 관찰된 타임스탬프 및
횟수를 포함한다.

## 프로파일 개요 {#profiles-overview}

프로파일은 로그, 메트릭, 트레이스와 함께 옵저버빌리티(observability)의 네 번째
필수 시그널로 부상하고 있다. 프로파일은 시스템 및 애플리케이션 동작에 대해 비할
데 없는 통찰(insight)을 제공하며, 종종 다른 시그널이 놓치는 성능
병목(bottleneck)을 발견해낸다.

프로파일은 리소스 소비와 코드 실행에 대한 세밀하고 시간 기반의 관점(view)을
제공하며, 여기에는 다음이 포함된다:

- **애플리케이션 수준 프로파일링(Application-level profiling)**: 소프트웨어
  함수가 CPU, 메모리 및 기타 리소스를 어떻게 소비하는지 드러내어, 느리거나
  비효율적인 코드를 강조해서 보여준다.

- **시스템 수준 프로파일링(System-level profiling)**: 인프라에 대한 전체적인
  관점을 제공하며, 운영체제 호출, 커널 작업, I/O에서 발생하는 문제를 정확히
  짚어낸다.

이러한 성능 정보를 통해 다음과 같은 효과를 얻을 수 있다:

- **더 빠른 근본 원인 분석(Root Cause Analysis)**: 성능 저하의 정확한 원인을
  신속하게 파악한다.
- **선제적 최적화(Proactive Optimization)**: 사용자에게 영향을 미치기 전에
  잠재적인 문제를 식별한다.
- **향상된 리소스 활용도(Improved Resource Utilization)**: 비용 절감과 효율성을
  위해 인프라를 최적화한다.
- **향상된 개발자 생산성(Enhanced Developer Productivity)**: 개발자가 코드
  성능을 검증하고 회귀(regression)를 방지할 수 있도록 돕는다.

## 프로파일이 다른 시그널을 보완하는 방법 {#how-profiles-complement-other-signals}

각 오픈텔레메트리 시그널은 서로 다른 질문에 답한다:

| 시그널       | 질문                                                              |
| ------------ | ----------------------------------------------------------------- |
| **로그**     | 어떤 개별 이벤트가 발생했는가? (시스템 동작에 대한 통찰)          |
| **메트릭**   | 시스템 수준에서 무슨 일이 일어나고 있는가? (예: CPU 사용률이 90%) |
| **트레이스** | 요청이 분산 시스템을 어떻게 통과하는가?                           |
| **프로파일** | 어떤 코드가 리소스 소비를 담당하는가?                             |

오픈텔레메트리 프로파일은 다른 시그널과의 양방향 링크(bi-directional link)를
지원한다. 이러한 상관관계(correlation)는 두 가지 차원에서 작동한다:

- **요청 컨텍스트 상관관계(Request context correlation)**: 프로파일링 데이터를
  특정 트레이스나 스팬에 연결하여, 특정 요청 중에 어떤 코드가 실행되고 있었는지
  확인할 수 있게 한다.

- **리소스 컨텍스트 상관관계(Resource context correlation)**: 프로파일링
  데이터를 동일한 서비스 인스턴스와 같이, 관련 메트릭, 로그, 트레이스를 발생시킨
  것과 동일한 [리소스](/docs/concepts/resources/)에 연결한다.

프로파일은 다른 시그널과 상관관계를 맺을 때 특히 강력해진다:

- **로그에서 프로파일로(Logs to profiles)**: 메모리 부족(out of memory) 로그
  항목에서 메모리 압박(memory pressure)을 유발한 코드 경로를 찾아낸다.
- **메트릭에서 프로파일로(Metrics to profiles)**: CPU나 메모리 사용량의
  급증(spike)에서 해당 리소스를 소비하는 함수로 바로 이동한다.
- **트레이스에서 프로파일로(Traces to profiles)**: 트레이스 내의 느린 스팬에서
  해당 프로파일을 확인하여 지연(latency)을 유발한 코드를 식별한다.

## 프로파일 유형 {#profile-types}

프로파일링은 다양한 종류의 리소스 사용량을 캡처할 수 있다. 일반적인 프로파일
유형에는 다음이 포함된다:

- **On-CPU**: 어떤 함수가 프로세서 시간을 소비하고 있는가?
- **Off-CPU**: 스레드가 실행되지 않고 어디서 블로킹되거나 대기(예: 락, I/O)하고
  있는가?
- **Heap (memory)**: 어떤 함수가 아직 사용 중인 메모리를 할당했는가?
- **Allocations (memory)**: 어떤 코드 경로가 가장 많은 메모리 할당을
  발생시키는가(해당 메모리가 해제되었는지 여부와 관계없이)?

오픈텔레메트리 프로파일 시그널은 이 모든 유형을 수용할 수 있을 만큼 유연하다.
다만 실제로 사용 가능한 프로파일 유형은 사용 중인 언어 런타임과
프로파일러(profiler)에 따라 달라진다.

## 프로파일링 동작 방식 {#how-profiling-works}

프로파일을 수집(collect)하는 방법에는 여러 가지 접근 방식이 있으며,
오픈텔레메트리 프로파일은 이 모든 방식을 지원하도록 설계되었다:

- **샘플링 기반 프로파일링(Sampling-based profiling)**: 프로파일러가 예를 들어
  타이머 기반 인터럽트(timer-based interrupt)를 사용해 주기적으로 프로그램을
  중단시키고, 현재 스택 트레이스를 기록한다. 이는 CPU 프로파일링에 가장 흔히
  사용되는 방식이다. 리눅스에서는 프로파일러가 eBPF를 사용하여 사용자
  공간(userspace) 애플리케이션을 전혀 수정하지 않고도 커널에서 스택 트레이스를
  캡처할 수 있다. 이 방식은 무계측(zero-instrumentation) 전체 시스템
  프로파일링(런타임 지원 없이 컴파일된 언어로 만들어진 코드를 포함하여)을
  가능하게 하며, 지속적이고 오버헤드가 낮은 프로덕션 환경에서의 사용을 위해
  설계되었다.
- **계측 기반 프로파일링(Instrumentation-based profiling)**: 런타임 훅(hook)
  또는 바이트코드 계측(bytecode instrumentation)이 메모리 할당, 락 획득, 가비지
  컬렉션과 같은 이벤트를 관련 스택 트레이스와 함께 보고한다.

수집 방식과 관계없이, 결과 데이터는 오픈텔레메트리의 공통 프로파일 데이터 모델로
직렬화(serialize)되어 OTLP를 통해 내보내진다(export).

## 프로파일 수집하기 {#collecting-profiles}

오픈텔레메트리는 리눅스용
[eBPF 기반 프로파일링 에이전트](https://github.com/open-telemetry/opentelemetry-ebpf-profiler)를
제공하며, 코드 변경 없이도 대부분의 언어를 프로파일링할 수 있다.

Java의 JFR이나 Go의 pprof와 같이 내장된 런타임 프로파일링 프레임워크를 활용하는
언어별 프로파일링 통합(integration) 기능도 이 시그널이 성숙해짐에 따라 추가로
제공될 예정이다.

프로파일은 OTLP를 통해 오픈텔레메트리 컬렉터로 내보내거나(export), 호환되는
백엔드로 직접 내보낼 수 있다.
