## 소개 {#introduction}

OBI의 분산 트레이싱(distributed tracing)은 두 부분으로 구성된다.

1. 나가는 작업에 대한 활성 부모 요청을 찾는다.
2. 선택된 W3C `traceparent` 값을 나가는 요청에 전파한다.

[분산 트레이스](../distributed-traces/) 가이드는 OBI가 나가는 HTTP/gRPC 트래픽에
트레이스 컨텍스트를 기록하는 방법을 설명한다. 이 페이지는 첫 번째 부분, 즉 OBI가
나가는 요청을 그 요청을 유발한 들어오는 요청과 연관시키는 방법과 그 연관이
실패할 수 있는 지점을 설명한다.

OBI는 eBPF와 런타임 관찰을 통해 이 연관을 수행한다. 임의의 애플리케이션 변수나
프레임워크 컨텍스트 객체를 읽지 않는다. 대신 아래에 설명된, 지원되는 런타임
핸드오프(hand-off) 메커니즘, 소켓 활동, OS 스레드 관계를 사용한다.

## OBI가 부모 요청을 찾는 방법 {#how-obi-finds-the-parent-request}

OBI가 나가는 요청을 관찰하면, 현재 처리 중인 들어오는 요청에 속한 부모 트레이스
컨텍스트를 찾는다. OBI는 사용할 수 있는 경우 런타임별 연관 데이터를 우선한다.
런타임별 일치가 없으면 OBI는 언어 중립적인(language-agnostic) OS 스레드 및 소켓
시그널로 폴백한다.

연관 단계는 나가는 `traceparent` 값을 기록하는 단계와 별개이다. 예를 들어 언어
중립적인 네트워크 수준 컨텍스트 전파는 HTTP/1.x와 HTTP/2를 통한 gRPC를
지원하지만, gRPC가 아닌 일반 HTTP/2 트래픽은 지원하지 않는다. Go 라이브러리 수준
컨텍스트 전파는 새로운 비-HTTPS 연결에서만 HTTP/2와 gRPC에 대한 컨텍스트를
기록할 수 있으며, 재사용된 HTTP/2/gRPC 연결은 아직 지원되지 않는다. 기타 제한
사항은
[분산 트레이스](../distributed-traces/#go-context-propagation-by-instrumenting-at-library-level)에
문서화되어 있다.

## 런타임별 연관 {#runtime-specific-association}

OBI는 일반적인 비동기 및 스레드 기반 실행 모델에 대해 런타임별 지원을 제공한다.

| 런타임 또는 구성 요소 | 연관 메커니즘                                                                                                              | 지원 범위 및 제한 사항                                                                                                                                              |
| :-------------------- | :------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Go                    | 고루틴 전반에 걸쳐 트레이스 컨텍스트를 추적한다.                                                                           | Go `1.18+`. 최대 6단계까지 중첩된 고루틴을 지원한다.                                                                                                                |
| Node.js               | Node.js async hooks를 사용하여 비동기 콜백 전에 활성 요청 컨텍스트를 갱신하고, 나가는 소켓을 들어오는 소켓과 연관시킨다.   | Node.js `8.0+`. `SIGUSR1`에 대한 커스텀 처리가 OBI의 Node.js 지원을 방해할 수 있다.                                                                                 |
| Java                  | `Executor`, `Runnable`, `Callable`, `ForkJoinTask`를 포함한 일반적인 JDK 태스크 API를 통한 핸드오프를 추적한다.            | JDK `8+`. 최대 3단계 핸드오프까지 태스크 부모 조회를 지원한다. 이러한 태스크 API를 사용하지 않는 커스텀 큐나 스케줄러 구현은 언어 중립적인 동작으로 폴백할 수 있다. |
| Java 가상 스레드      | 가상 스레드의 마운트 및 언마운트 작업을 추적하여, 요청 컨텍스트가 캐리어 OS 스레드뿐 아니라 가상 스레드에 연결되도록 한다. | JDK `21+`. 가상 스레드에서 처리되는 요청에는 로그 보강(enrichment)이 생략된다.                                                                                      |
| Python asyncio        | 현재 `asyncio` 태스크, 자식 태스크 생성, 상속된 컨텍스트, `asyncio.to_thread()` 작업을 추적한다.                           | `uvloop` 이벤트 루프를 사용하는 Python `3.9+`에서 지원된다.                                                                                                         |
| Ruby Puma             | Puma의 리액터(reactor) 스레드가 수락한 작업을 워커 스레드로 넘길 때 요청을 연관시킨다.                                     | Puma `5.0+`가 필요하다. Puma로 서비스되지 않는 Ruby 서비스는 언어 중립적인 동작을 사용한다.                                                                         |
| NGINX                 | 들어오는 요청을 NGINX가 선택한 업스트림(upstream) 연결과 연관시킨다.                                                       | OBI가 관찰하는 NGINX 업스트림 프록시에 적용된다.                                                                                                                    |

이러한 메커니즘은 일반적인 프레임워크 동작을 위해 설계되었다. 예를 들어 OBI는
보통 다음의 경우에 부모 스팬과 자식 스팬을 연관시킬 수 있다.

- 요청을 처리하는 동안 짧은 고루틴 트리를 생성하는 Go 핸들러.
- 표준 Node.js 비동기 런타임을 사용하는 Node.js HTTP 프레임워크.
- 나가는 작업이 요청 스레드에 머무르거나 위에 나열된 일반적인 JDK 태스크 API를
  통해 디스패치되는, 많은 Spring MVC 서비스와 같은 Java 서블릿 스타일
  애플리케이션.
- `asyncio.create_task()`, `asyncio.gather()`, `asyncio.to_thread()`로 생성된
  작업을 포함하여 `uvloop`에서 실행되는 Python `asyncio` 서비스.
- Puma로 서비스되는 Ruby 애플리케이션.
- 업스트림 서비스로 향하는 NGINX 리버스 프록시 요청.

## 언어 중립적인 연관 {#language-agnostic-association}

런타임별 연관을 사용할 수 없으면, OBI는 eBPF에서 볼 수 있는 언어 중립적인
시그널을 사용한다.

- 동일한 OS 스레드가 들어오는 요청과 나가는 요청을 처리한다.
- 나가는 요청이 OBI가 원래 요청 스레드와 연결할 수 있는 자식 스레드나
  프로세스에서 이루어진다.
- 나가는 요청이 다른 워커 스레드에 의해 완료되기 전에, 요청 스레드가 소켓
  설정이나 연결 활성 확인을 수행한다.

이 폴백을 통해 OBI는 언어별 코드 없이 많은 동기 프레임워크와 일부 스레드 풀
패턴을 처리할 수 있다. 이는 의도적으로 제한되어 있다. OBI는 지원되는 관찰에서
보이지 않는 임의의 애플리케이션 큐, 사용자 공간 스케줄러, 프레임워크별 컨텍스트
객체를 재구성하려고 시도하지 않는다.

## 제한 사항 {#limitations}

애플리케이션이 OBI가 관찰할 수 없는 방식으로 작업을 이동하면 OBI는 부모-자식
연관을 놓칠 수 있다. 일반적인 경우는 다음과 같다.

- 작업이 프레임워크 큐에 배치되고, 모든 나가는 소켓 활동이 나중에 OBI가 원래
  요청과 연결할 수 없는 워커 스레드에서 발생한다.
- 리액티브(reactive) 또는 이벤트 루프 프레임워크가 위의 런타임별 메커니즘이
  다루지 않는 스케줄링 구조를 통해 작업을 전달한다. Spring WebFlux,
  Netty/Reactor, 커스텀 Java 스케줄러는 핸드오프가 관찰되는 JDK 태스크 API나
  언어 중립적인 소켓 시그널도 거치지 않는 한 여전히 연관을 놓칠 수 있다.
- 백그라운드 작업, 재시도, 지연된 태스크가 원래 요청 컨텍스트가 더 이상 활성
  상태가 아닌 후에도 계속된다.
- 여러 논리적 요청이 동일한 OS 스레드에서 다중화되고, 활성 논리적 태스크를
  식별할 수 있는 지원되는 런타임별 메커니즘이 없다.
- 활성 컨텍스트 전파 방식이 나가는 프로토콜에 대한 트레이스 컨텍스트를 기록할 수
  없다. 특히 언어 중립적인 네트워크 수준 전파는 gRPC가 아닌 일반 HTTP/2 트래픽을
  지원하지 않는다.

부모 연관이 실패하더라도 OBI는 관찰된 들어오는 요청과 나가는 요청에 대한 스팬을
여전히 보고할 수 있지만, 나가는 요청은 새로운 트레이스를 시작하거나 애플리케이션
수준 프레임워크가 선택했을 것과 다른 부모에 연결될 수 있다.
