오픈텔레메트리(OpenTelemetry) Java 에이전트는 애플리케이션과 동일한 Java 가상
머신(JVM) 안에서 실행되어 애플리케이션을 계측한다. 다른 소프트웨어 에이전트와
마찬가지로, Java 에이전트는 CPU, 메모리, 네트워크 대역폭 같은 시스템 리소스를
필요로 한다. 에이전트가 리소스를 사용하는 것을 에이전트 오버헤드 또는 성능
오버헤드라고 한다. 오픈텔레메트리 Java 에이전트는 JVM 애플리케이션을 계측할 때
시스템 성능에 미치는 영향이 매우 작지만, 최종적인 에이전트 오버헤드는 여러
요인에 따라 달라진다.

에이전트 오버헤드를 늘릴 수 있는 일부 요인은 물리 머신 아키텍처, CPU 주파수,
메모리 용량과 속도, 시스템 온도, 리소스 경합 등 환경적인 것이다. 그 밖의
요인으로는 가상화와 컨테이너화, 운영체제와 그 라이브러리, JVM 버전과 벤더, JVM
설정, 모니터링 대상 소프트웨어의 알고리즘 설계, 소프트웨어 의존성 등이 있다.

현대 소프트웨어의 복잡성과 배포 시나리오의 폭넓은 다양성 때문에, 단일한 에이전트
오버헤드 추정치를 내놓는 것은 불가능하다. 특정 배포에서 어떤 계측 에이전트의
오버헤드를 알아내려면, 직접 실험을 수행하고 측정값을 수집해야 한다. 따라서
성능에 대한 모든 진술은 특정 시스템에서의 평가를 전제로 하는 일반적인 정보이자
가이드라인으로 취급한다.

다음 섹션에서는 오픈텔레메트리 Java 에이전트의 최소 요구사항, 성능에 영향을 줄
수 있는 잠재적 제약, 그리고 에이전트의 성능을 최적화하고 문제를 해결하기 위한
가이드라인을 설명한다.

## 에이전트 오버헤드를 줄이기 위한 가이드라인 {#guidelines-to-reduce-agent-overhead}

다음의 모범 사례와 기법은 Java 에이전트로 인한 오버헤드를 줄이는 데 도움이 될 수
있다.

### 트레이스 샘플링 구성하기 {#configure-trace-sampling}

계측이 처리하는 스팬의 양은 에이전트 오버헤드에 영향을 줄 수 있다. 트레이스
샘플링을 구성하여 스팬 양을 조정하고 리소스 사용량을 줄일 수 있다.
[샘플링](/docs/languages/java/sdk/#sampler)을 참고한다.

### 특정 계측 끄기 {#turn-off-specific-instrumentations}

필요하지 않거나 너무 많은 스팬을 생성하는 계측을 꺼서 에이전트 오버헤드를 더
줄일 수 있다. 계측을 끄려면 `-Dotel.instrumentation.<name>.enabled=false` 또는
`OTEL_INSTRUMENTATION_<NAME>_ENABLED` 환경 변수를 사용한다. 여기서 `<name>`은
계측의 이름이다.

예를 들어 다음 옵션은 JDBC 계측을 끈다.
`-Dotel.instrumentation.jdbc.enabled=false`

### 애플리케이션에 더 많은 메모리 할당하기 {#allocate-more-memory-for-the-application}

`-Xmx<size>` 옵션으로 JVM의 최대 힙 크기를 늘리면, 계측이 메모리에 수명이 짧은
객체를 많이 생성할 수 있으므로 에이전트 오버헤드 문제를 완화하는 데 도움이 될 수
있다.

### 수동 계측을 필요한 만큼으로 줄이기 {#reduce-manual-instrumentation-to-what-you-need}

과도한 수동 계측은 에이전트 오버헤드를 늘리는 비효율을 초래할 수 있다. 예를 들어
모든 메서드에 `@WithSpan`을 사용하면 스팬 양이 많아지고, 이는 데이터의 노이즈를
늘리며 시스템 리소스를 더 소비한다.

### 충분한 리소스 프로비저닝하기 {#provision-adequate-resources}

계측과 컬렉터를 위해 충분한 리소스를 프로비저닝한다. 메모리나 디스크 같은
리소스의 양은 애플리케이션 아키텍처와 요구사항에 따라 달라진다. 예를 들어 계측된
애플리케이션을 오픈텔레메트리 컬렉터와 같은 호스트에서 실행하는 것이 흔한
구성이다. 이 경우, 컬렉터의 리소스를 적정 규모로 산정하고 설정을 최적화하는 것을
고려한다. [스케일링](/docs/collector/scaling/)을 참고한다.

## Java 에이전트의 성능에 영향을 주는 제약 {#constraints-impacting-the-performance-of-the-java-agent}

일반적으로 애플리케이션에서 더 많은 텔레메트리를 수집할수록 에이전트 오버헤드에
미치는 영향이 커진다. 예를 들어 애플리케이션과 관련 없는 메서드를 트레이싱하는
것은, 그런 메서드를 트레이싱하는 것이 메서드 자체를 실행하는 것보다 연산적으로
더 비싸기 때문에 상당한 에이전트 오버헤드를 일으킬 수 있다. 마찬가지로 메트릭의
높은 카디널리티 태그는 메모리 사용량을 늘릴 수 있다. 디버그 로깅을 켜면 디스크
쓰기 작업과 메모리 사용량도 늘어난다.

JDBC나 Redis 같은 일부 계측은 높은 스팬 양을 생성하여 에이전트 오버헤드를
늘린다. 불필요한 계측을 끄는 방법에 대한 자세한 내용은
[특정 계측 끄기](#turn-off-specific-instrumentations)를 참고한다.

> [!NOTE]
>
> Java 에이전트의 실험적 기능은 성능보다 기능에 초점을 맞추는 실험적 특성 때문에
> 에이전트 오버헤드를 늘릴 수 있다. 안정적인 기능은 에이전트 오버헤드 측면에서
> 더 안전하다.

## 에이전트 오버헤드 문제 해결하기 {#troubleshooting-agent-overhead-issues}

에이전트 오버헤드 문제를 해결할 때는 다음을 수행한다.

- 최소 요구사항을 확인한다.
  [사전 요구사항](/docs/languages/java/getting-started/#prerequisites)을
  참고한다.
- 호환되는 최신 버전의 Java 에이전트를 사용한다.
- 호환되는 최신 버전의 JVM을 사용한다.

에이전트 오버헤드를 줄이기 위해 다음 조치를 고려한다.

- 애플리케이션이 메모리 한계에 가까워지고 있다면 메모리를 더 준다.
- 애플리케이션이 모든 CPU를 사용하고 있다면 수평으로 확장하는 것이 좋다.
- 메트릭을 끄거나 튜닝해 본다.
- 트레이스 샘플링 설정을 튜닝하여 스팬 양을 줄인다.
- 특정 계측을 끈다.
- 불필요한 스팬 생성이 없는지 수동 계측을 검토한다.

## 에이전트 오버헤드 측정을 위한 가이드라인 {#guidelines-for-measuring-agent-overhead}

자신의 환경과 배포에서 에이전트 오버헤드를 측정하면 계측이 애플리케이션이나
서비스의 성능에 미치는 영향에 대한 정확한 데이터를 얻을 수 있다. 다음
가이드라인은 신뢰할 수 있는 에이전트 오버헤드 측정값을 수집하고 비교하기 위한
일반적인 단계를 설명한다.

### 무엇을 측정할지 결정하기 {#decide-what-you-want-to-measure}

애플리케이션이나 서비스의 사용자마다 에이전트 오버헤드의 서로 다른 측면을 느낄
수 있다. 예를 들어 최종 사용자는 서비스 지연 시간의 저하를 느낄 수 있는 반면,
무거운 워크로드를 다루는 파워 유저는 CPU 오버헤드에 더 주의를 기울인다. 한편
예를 들어 탄력적 워크로드로 인해 자주 배포하는 사용자는 시작 시간에 더 많이 신경
쓴다.

측정 대상을 사용자 경험에 확실히 영향을 주는 요인으로 좁혀, 데이터셋에 관련 없는
정보가 들어가지 않도록 한다. 측정값의 예로는 다음과 같은 것이 있다.

- 사용자 평균, 사용자 피크, 머신 평균 CPU 사용량
- 총 할당 메모리와 사용된 최대 힙
- 가비지 컬렉션 일시 중지 시간
- 밀리초 단위의 시작 시간
- 평균 및 95 백분위수(p95) 서비스 지연 시간
- 네트워크 읽기 및 쓰기 평균 처리량

### 적합한 테스트 환경 준비하기 {#prepare-a-suitable-test-environment}

통제된 테스트 환경에서 에이전트 오버헤드를 측정하면 성능에 영향을 주는 요인을 더
잘 식별할 수 있다. 테스트 환경을 준비할 때는 다음을 완료한다.

1.  테스트 환경의 구성이 프로덕션과 유사한지 확인한다.
2.  테스트 대상 애플리케이션을 간섭할 수 있는 다른 서비스로부터 격리한다.
3.  애플리케이션 호스트에서 불필요한 모든 시스템 서비스를 끄거나 제거한다.
4.  애플리케이션이 테스트 워크로드를 처리할 만큼 충분한 시스템 리소스를 갖추도록
    한다.

### 현실적인 테스트 묶음 만들기 {#create-a-battery-of-realistic-tests}

테스트 환경에 대해 실행하는 테스트는 가능한 한 일반적인 워크로드와 비슷하게
설계한다. 예를 들어 서비스의 일부 REST API 엔드포인트가 높은 요청량에
취약하다면, 무거운 네트워크 트래픽을 시뮬레이션하는 테스트를 만든다.

Java 애플리케이션의 경우, 측정을 시작하기 전에 워밍업 단계를 사용한다. JVM은
JIT(just-in-time) 컴파일을 통해 수많은 최적화를 수행하는 매우 동적인 머신이다.
워밍업 단계는 애플리케이션이 대부분의 클래스 로딩을 마치도록 돕고, JIT
컴파일러가 대부분의 최적화를 실행할 시간을 준다.

많은 수의 요청을 실행하고 테스트 패스를 여러 번 반복한다. 이 반복은 대표성 있는
데이터 샘플을 확보하는 데 도움이 된다. 테스트 데이터에 오류 시나리오를 포함한다.
일반적인 워크로드와 유사한, 보통 2%에서 10% 사이의 오류율을 시뮬레이션한다.

> [!NOTE]
>
> 옵저버빌리티(observability) 백엔드나 기타 상용 서비스를 대상으로 할 때는
> 테스트가 비용을 늘릴 수 있다. 그에 맞게 테스트를 계획하거나, 자체 호스팅 또는
> 로컬 실행 백엔드 같은 대안을 사용하는 것을 고려한다.

### 비교 가능한 측정값 수집하기 {#collect-comparable-measurements}

어떤 요인이 성능에 영향을 주고 에이전트 오버헤드를 유발하는지 식별하려면, 단일
요인이나 조건을 수정한 뒤 같은 환경에서 측정값을 수집한다.

### 에이전트 오버헤드 데이터 분석하기 {#analyze-the-agent-overhead-data}

여러 패스에서 데이터를 수집한 뒤, 결과를 차트로 그리거나 통계 검정으로 평균을
비교하여 유의미한 차이가 있는지 확인할 수 있다.

서로 다른 스택, 애플리케이션, 환경은 서로 다른 운영 특성과 서로 다른 에이전트
오버헤드 측정 결과로 이어질 수 있다는 점을 고려한다.
