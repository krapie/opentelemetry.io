## 요약 {#summary}

오픈텔레메트리(OpenTelemetry) 커뮤니티 데모 애플리케이션은 프로덕션 수준에
준하는(production-lite) 클라우드 네이티브 애플리케이션에서 오픈텔레메트리 API,
SDK, 도구를 보여주는 쇼케이스가 되는 것을 목표로 한다. 이 애플리케이션의 전체
목표는 오픈텔레메트리 구성 요소의 정형화된 '데모'를 제공하는 데 그치지 않고,
최종 사용자, 벤더, 그 밖의 이해관계자가 추가로 커스터마이징할 수 있는 프레임워크
역할을 하는 것이다.

### 요구사항 {#requirements}

- [애플리케이션 요구사항](../application/)
- [오픈텔레메트리 요구사항](../opentelemetry/)
- [시스템 요구사항](../system/)

### 애플리케이션 목표 {#application-goals}

- 개발자에게 오픈텔레메트리 계측을 학습하는 데 사용할 수 있는 견고한 샘플
  애플리케이션을 제공한다.
- 옵저버빌리티 벤더에게 추가로 커스터마이징(또는 그대로(OOB) 사용)할 수 있는, 잘
  지원되는 단일 데모 플랫폼을 제공한다.
- 오픈텔레메트리 커뮤니티에 OTel API, SDK, 도구의 기능과 역량을 보여주는
  살아있는 아티팩트(artifact)를 제공한다.
- 오픈텔레메트리 관리자(maintainer)와 워킹 그룹(WG)에게 새로운 기능/개념을 '실제
  환경에서' 시연할 수 있는 플랫폼을 제공한다.

다음은 데모 애플리케이션의 논리적 구성 요소에 대한 일반적인 설명이다.

## 메인 애플리케이션 {#main-application}

데모 앱의 대부분은 전자상거래 사이트와 같이 유용한 '실제 세계'의 작업을
수행하는, 독립적인 마이크로서비스 기반 애플리케이션이다. 이 애플리케이션은
gRPC와 HTTP를 통해 서로 통신하는 여러 서비스로 구성되며, 쿠버네티스(또는
로컬에서는 Docker)에서 실행된다.

각 서비스는 트레이스, 메트릭, 로그에 대해(적용 가능하고 사용 가능한 범위 내에서)
오픈텔레메트리로 계측되어야 한다.

각 서비스는 동일한 gRPC 엔드포인트를 구현하되 다른 언어/구현으로 작성된, 동일한
비즈니스 로직을 수행하는 서비스와 상호 교체 가능해야 한다.

각 서비스는 분산 애플리케이션에서 텔레메트리가 문제 해결에 어떻게 도움이 되는지
보여주는 데 사용할 수 있는 결함을 활성화/비활성화하기 위해 기능 플래그(feature
flag) 서비스와 통신할 수 있어야 한다.

## 기능 플래그 구성 요소 {#feature-flag-component}

기능 플래그는 클라우드 네이티브 애플리케이션 개발에서 중요한 부분이다. 이 데모는
기능 플래그를 관리하기 위해 CNCF 인큐베이팅(incubating) 프로젝트인 OpenFeature를
사용한다.

기능 플래그는 flagd 구성기(configurator) 사용자 인터페이스를 통해 설정할 수
있다.

## 오케스트레이션과 배포 {#orchestration-and-deployment}

모든 서비스는 쿠버네티스에서 실행된다. 오픈텔레메트리 컬렉터는 오픈텔레메트리
오퍼레이터(Operator)를 통해 배포되어야 하며, 사이드카(sidecar) +
게이트웨이(gateway) 모드로 실행되어야 한다. 각 파드의 텔레메트리는 에이전트에서
게이트웨이로 라우팅되어야 하며, 게이트웨이는 기본적으로 오픈 소스 트레이스 +
메트릭 시각화 도구로 텔레메트리를 내보내야 한다.

로컬/비-쿠버네티스 배포의 경우, 컬렉터는 컴포즈(compose) 파일을 통해 배포되어야
하며, 애플리케이션의 트레이스/메트릭뿐만 아니라 `dockerstatsreceiver`를 통해
Docker 컨테이너도 모니터링해야 한다.

이 프로젝트의 설계 목표 중 하나는 클라우드 환경으로 셀프 배포하기 위한 CI/CD
파이프라인을 포함하는 것이다. 로컬 개발 환경에서는 이를 생략할 수 있다.
